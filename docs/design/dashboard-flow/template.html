04 / THE MOMENTS THAT BUILD TRUST

No dead ends. No guessing.

Pick a state below. The interface should explain what happened and what you can do next.

APPLICATION REVIEWSIMULATED STATES
FAST TO FEEL

Acknowledge immediately.

Proposed targets: visible click feedback within 100 ms; a stable skeleton if a load exceeds 300 ms; a timeout with recovery after 10 seconds. Measure on an agreed phone and network before calling it fast.

FAST TO WORK

Keep your place.

Preserve list filters, sorting and scroll when returning from a record. Paginate data, load heavy previews on demand, and refresh only the section that changed. Never blank the whole workspace during a save.

SAFE TO TRUST

Confirm what is true.

Only show Saved after the server confirms. Publishing, invitations, finance and permission changes need explicit outcomes, safe retries and history. A failed save keeps the draft.

EASY TO USE

Make access universal.

Visible focus, keyboard paths, labeled fields, text with status colors, clear error summaries and reduced motion. On phones, use stacked records and a full-screen editor; keep the main action reachable.

See the acceptance checklist for every screen
  • Loading, true empty, filtered empty, unavailable and forbidden states are distinct.
  • Actions cannot submit twice; permission checks and version checks are enforced on the server.
  • Validation appears beside the field and is announced; focus moves to the first problem.
  • Unsaved changes require Stay or Discard before navigation; destructive actions name the affected record.
  • Keyboard, screen reader, reduced motion, 320px phone and desktop are verified with realistic content.
  • Session expiry reauthenticates safely; no sensitive drafts or tokens are written to localStorage.
  • Timezone, money currency, permission audience and current-vs-period metrics are explicit.
  • Performance targets are measured against the agreed data size and network before release.

05 / AFTER YOUR REVIEW

Build in useful slices.

Finish and test one connected journey at a time. Reuse working backend behavior.

WE CAN MOVE NOW

The common experience.

Approve the shell and navigation, then refine attention → queue → review → saved result. Standardize forms, mobile layouts, feedback, retry and conflict behavior. Strengthen sign-in and account security without inventing membership policy.

WE NEED THE TEAM FOR

The meaning behind the controls.

Membership eligibility and approval; staff responsibilities; document audiences; finance categories and verification; project completion criteria; report definitions and support ownership. These decisions gate the affected action—not every screen.

Review → revise → approve a journey → build → verify

Launch remains a separate milestone: production mail, Railway setup (currently deferred), migrations/backups, monitoring, security verification, documentation and staff training. A polished prototype does not complete those obligations.
